### Added
- **Signed draw receipts: the enforcement point now hands evidence back up the delegation chain.** #432 sent authority *downstream* — a parent narrows a Biscuit and hands it to a delegate; this closes the return path. Every `/gateway/enforce` request presenting a mandate Biscuit gets a signed receipt in the response: the gateway's attestation of what was done — or refused — with that authority, so a delegator ends up holding offline-verifiable proof of its delegate's actions without anyone instrumenting the delegate's runtime. Receipts are Ed25519 signatures over an RFC 8785-canonicalized payload, signed with the *same root key that anchors the tokens* (one published key verifies both directions), and they name the revocation id of the exact token copy presented — a parent's receipt provably concerns its delegate's attenuated token — plus the request's correlation id, tying the receipt to the chained audit rows so it reconciles against the tamper-evident ledger on dispute. Denials get receipts too: "your delegate tried and was refused" is evidence the delegator wants, with the failing check named. Best-effort by design (an unsignable receipt returns null rather than failing the request it evidences), and inert without `BISCUIT_ROOT_KEY_PEM`, same as the token layer. New `common/biscuit/receipts.py`; forgery coverage includes tampered payloads and key-substitution attacks; the demo walk now verifies each receipt offline as the delegator would. (#433)
- **Mandates can cross trust domains as offline-attenuable Biscuit tokens, enforced at the gateway — the first gateway↔Mandate Service bridge.** A mandate's grant (spend ceiling, scope, subject, validity window) can now be minted as an [Eclipse Biscuit](https://www.biscuitsec.org/) presentation token (`POST /api/v1/mandates/{id}/biscuit`): Ed25519-signed, carrying the grant as readable Datalog, and narrowable offline — a parent agent appends a tighter per-request ceiling and hands the token to a sub-agent with no call to any service; rights only ever shrink. The gateway accepts it via a new `X-Agent-Mandate` header on `/gateway/enforce` as a two-layer check: the token's own checks run locally before policy eval (an over-ceiling draw by a delegate is denied by the token itself — the Mandate Service is never consulted), and the authoritative draw settles against the Mandate Service after policy ALLOW, behind its own circuit breaker with new fail-closed deny reasons (`biscuit_denied`, `mandate_denied`, `mandate_unavailable`). The design split is deliberate: the token carries authority, the service carries cumulative state (a copyable offline token cannot count), and the chained audit log carries evidence — biscuit rows record per-token revocation ids, so the chain shows *which copy* of the authority was presented. Two Datalog rules worth knowing came out of testing and a live production run: token-side informational facts must never share a name with verifier-queried facts (or the token satisfies its own checks — pinned by a fact-injection test), and the grant ceiling reads `$a <= limit or settlement(true)` so already-moved money is recordable past the grant as an `exceeded` breach — only the verifier may assert `settlement(true)`, and attenuation caps deliberately have no such escape. Inert without configuration (`BISCUIT_ROOT_KEY_PEM` unset → mint 503s, no header → nothing changes); shared logic in `common/biscuit/`; runnable walk in `scripts/demo_biscuit_trust_boundary.py`; `biscuit-python==0.4.0` pinned with both service locks regenerated. Migration `e2f3a4b5c6d7` (two additive nullable columns) + `scripts/backfill_key_fingerprints.py` stamps legacy rows (metadata-only, dry-run supported). Bundle README documents key epochs. Already-issued bundles verify exactly as before.
- **OCSF export: genesis event no longer emits the literal `GENESIS` sentinel as a fingerprint value.** The chain's first row stores `"GENESIS"` in `prev_hash`/`prev_hash_org`, and the emitter passed it through verbatim — producing a `prev_entry_hash` fingerprint whose `value` isn't a hash (`{"algorithm_id": 99, "algorithm": "HMAC-SHA-256", "value": "GENESIS"}`, seen in the production export at org chain seq 1). `select_chain` now treats the sentinel as a missing predecessor, so the genesis event simply omits `prev_entry_hash` — the same shape as a row with no chain history. Chain *verification* (CLI verifier, `common/audit`, backfill scripts) reads the raw DB columns and still uses the sentinel — unchanged. The reference-bundle validator (`regenerate.py`) keeps accepting the sentinel on seq 1 for backward compatibility with the already-shared bundle revision; the README honest-limitations note gets updated once a post-fix export is regenerated.
- **Case File verifier gives a "wrong file" hint instead of a false tamper alarm.** Dropping an `evidence-anchor/` file (`checkpoints.json` / `inclusion-proofs.json`) or a JWKS file onto the server-side "Verify a Case File" panel used to return "Chain broken / Signature invalid" — reading like tampering rather than the wrong file, a bad moment in a live court/customer demo. The panel now sniffs the JSON client-side *before* uploading (`sniffCaseFile`): a real Case File report is an object carrying the audit `events[]`/`entries[]`; a bare array is `checkpoints.json`, `{proofs}` is `inclusion-proofs.json`, `{keys}` is a JWKS file — wrong files get a friendly message routing the user to the inclusion verifier, and invalid JSON is caught too. Valid reports upload exactly as before. Frontend only. (#357)
- _Forensics:_ the Evidence Anchor checkpoint cron no longer runs `SELECT DISTINCT org_id` over the whole `audit_log` table every tick and then probes every org. It now selects only orgs whose latest `audit_log.id` is ahead of their checkpoint high-water mark — one set-based query that skips idle orgs entirely and reuses the same mark to seed each drain (`after_id`), so the `max(last_audit_id)` lookup never runs separately. Follow-up to the #346 N+1 fix; the remaining P95-latency lever on `/api/internal/evidence-anchor/checkpoint`. The run-summary field `orgs_scanned` is now `orgs_with_backlog`. Internal tooling only — no product impact.
