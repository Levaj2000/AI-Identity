## [0.3.0] — 2026-08-04

### Security
- **Supply-chain phases 2+3: image builds can no longer reach PyPI — a deleted or yanked release cannot break a deploy.** Completes what phase 1's locks set up (below; sprint item #443, root cause: the 2026-07-24 `liboqs-python` yank, #405). The three deploy Dockerfiles now install with `--no-index --find-links=/wheelhouse --require-hashes` from their `requirements.lock` — pip is structurally incapable of contacting any package index during an image build, which is the acceptance criterion made a build flag rather than a promise. Wheels arrive via a new `populate-wheelhouse` composite action: per-lock `pip download` (the three locks are internally consistent but **not** jointly resolvable — `pyasn1-modules` differs between api and mandate) through the **`pypi-cache` Artifact Registry remote repository** (us-east1 pull-through proxy of PyPI, pre-warmed with all 89 locked package-versions, hash-checked in transit; cached artifacts keep serving after upstream deletion), with an `actions/cache` fast path keyed on the locks' hash — three layers deep before any build could notice PyPI missing. A new `image-build-check.yml` builds all three images hermetically on any PR touching Dockerfiles or locks, so a mistake surfaces pre-merge, not mid-deploy. Install order inside the images flipped (lock layer first, then `common/` with `--no-deps --no-build-isolation`): closes the same editable-install drift hole CI closed in phase 1, and stops every `common/` edit from busting the heavyweight pip layer — code-only deploys now rebuild images from a warm dependency layer. The vestigial root `cloudbuild.yaml` is **deleted** rather than left as a live non-hermetic build path: zero Cloud Build triggers exist (verified), the WIF SA holds no Cloud Build role, and `deploy-gke.yml` has always built on the runner (#411). Deliberately out of scope, documented in AGENTS.md: the root `Dockerfile` (docker-compose local dev) still installs from PyPI, and `agent/requirements.txt` remains unpinned — both off the GKE deploy path. Full operating notes in AGENTS.md "Dependency Locks & Hermetic Image Builds". full transitive lockfiles with hashes for the three deployed images.** The 2026-07-24 `liboqs-python` PyPI yank (see the pin-bump fix below, PR #405) broke every GKE deploy — and it hit a *direct* pin, the visible 40% of the problem: the ~78 direct pins across `api`/`gateway`/`mandate` resolve to **185 pinned distributions** once the transitive graph is included, and until now everything below the direct pins resolved live and unpinned on every image build (a yanked transitive dep would have failed builds with no fixable line in any file we control). Each service now carries a `requirements.lock` — full transitive pin set with `--hash` entries for every artifact, cross-resolved for the image platform (`--python-version 3.11 --python-platform x86_64-unknown-linux-gnu`, regeneration command in each lock's header) — verified: all 89 unique package-versions ship linux-compatible wheels, so no image needs a build toolchain to consume them. Two CI changes: a `lockfile-consistency` job runs `scripts/check_lockfiles.py`, which checks that every direct pin appears in the lock at the same version (deliberately *not* regenerate-and-diff — resolution of unpinned transitives moves as PyPI moves, so a byte-diff guard would fail spontaneously with no repo change); and `python-lint-test` now installs from the locks with `--require-hashes` (api+gateway locks verified co-installable) plus `--no-deps` on `common/`, so every CI run doubles as an installability test of the exact versions prod ships — this also closes a version-drift hole where `common/setup.py`'s open ranges (`sqlalchemy>=2.0`, `cryptography>=44.0`, …) resolved to latest at install time. **The Dockerfiles still install from live PyPI** — phase 2 (warming the `pypi-cache` Artifact Registry remote repo, already created) and phase 3 (hermetic `--no-index` image builds from a wheelhouse) make the builds yank-proof; this phase makes the dependency set exact, hash-checked, and CI-guarded.
- **The confidential-material guard now runs in CI, not only as a pre-commit hook.** `scripts/check-no-confidential.sh` was already wired into `.pre-commit-config.yaml` as the second line of defence behind `.gitignore`, but hooks live in a single clone and vanish with `--no-verify` — replacing the local checkout on 2026-07-27 left `.git/hooks` holding nothing but samples, so the guard had been inert. The script gains a `--range <base> <head>` mode (same path and email-hash patterns, one source of truth) and a new `no-confidential` CI job runs it over the PR diff — three-dot against the merge base, so a violation introduced in an early commit and left in place is still caught — and over direct pushes to `main`, which branch protection does not cover while `enforce_admins` is off. Verified against forced-add path hits, filename patterns at depth, a forbidden address in committed content (caught even after the worktree copy is scrubbed, since it reads the blob rather than the checkout), binaries, and a clean diff. Gating still requires adding **Public repo — no confidential material** to the required status checks on `main`.
- **Confidential GTM material removed from this public repo — and the loop that kept republishing it closed.** An exposure audit of the public repository found no leaked credentials (2,969 blobs scanned — every blob reachable from all refs across the full 683-commit history and all ~115 branches; every hit a test fixture or placeholder, and secrets live in Google Secret Manager referenced by name only), but the business was sitting next to the code: a live CRM export naming prospects, contacts, and candid deal risk (`marketing/sales/pipeline-snapshots/`), a design-partner outreach list with named CEOs, verified addresses, and verbatim cold-email drafts, per-account engagement folders, pricing sheets, a competitor teardown, a spend tracker (including a payment method and three unrelated side projects), and weekly internal status against targets. Two personal Gmail addresses were also published, one pair of them inside `PROTECTED_EMAILS` — the allowlist that stops the weekly cleanup cron from deleting those accounts — so the plaintext could not simply be deleted without making the accounts eligible for deletion. Protection is now two-layered: an env-configured list (`PROTECTED_EMAILS`) plus a hard-coded SHA-256 backstop, joined by `is_protected()`, which every deletion path filters through; **an unset env var can never mean "protect nobody"**, and matching is now case- and whitespace-insensitive (strictly more protective than the previous exact set-membership test). ### Fixed
- **Python SDK README quick-start showed policy rule keys the gateway never evaluates.** The example policy used `blocked_endpoints` and `max_tokens_per_request` — neither is a key `_evaluate_policy_rules` reads, so anyone following the public README would have attached a policy that silently enforces nothing (and, being fail-closed, denies everything). Replaced with the real keys: `allowed_endpoints` / `denied_endpoints` / `allowed_methods`. (#422)
- **Last 10 "tamper-proof" occurrences in `sdk/` corrected to "tamper-evident".** The #389 site-wide sweep covered the marketing site but missed the SDK tree — including `sdk/langchain`, the package LangChain's official docs link to, where the phrase sat in the PyPI package description, README, docstrings, and examples. Extends #389's terminology rule to the last untouched surface. (#422)
- **`/metrics` can no longer pin Neon awake — DB-backed gauge refresh throttled to epoch-aligned 15-minute windows; and GMP scraping unblocked after 107 silently dead days.** The scrape handler ran 6 aggregate Postgres queries on every scrape; at the PodMonitorings' 30s interval, any resumption of scraping would have reset Neon's ~5-minute autosuspend timer continuously and put the compute back on 24/7 uptime (~$83/mo — the same idle-uptime bug #416 fixed for `/health`). Gauges now refresh at most once per `METRICS_DB_GAUGE_TTL_SECONDS` (default 900s), bucketed by **wall clock** (`epoch // TTL`), not per-process age — with 8 serving processes (2 gunicorn workers × 2 pods × 2 services), independent TTLs drift into staggered refreshes that keep the compute awake anyway, while epoch-aligned 900s windows open at :00/:15/:30/:45, the instants the `*/15` evidence-anchor cron already wakes it, so refreshes add zero marginal awake time. Steady-state scrapes open no DB connection at all, which also removes the ~1.2s connection-acquisition cost behind the recurring PYTHON-FASTAPI-2 p95 alert; counters and histograms are in-process and unaffected. The reason none of this was billing today: **scraping has been dead since the PodMonitorings shipped** — the `allow-gmp-scrape` NetworkPolicy admits namespace `gmp-system` (Google's docs for Standard clusters), but this Autopilot cluster runs its collectors in `gke-gmp-system`, so `default-deny-all` dropped every scrape, unlogged, while PodMonitoring status read `ConfigurationCreateSuccess` (the collector's generated config carried both ai-identity jobs all along). The policy now admits both namespaces. Both fixes ship together deliberately: `deploy-gke.yml` applies the policy and rolls the throttled code in the same run, so scraping revives only alongside the fix. July's idle uptime therefore did **not** come from `/metrics` — if active time stays high post-merge, suspect real load. (#419)
- **Neon compute no longer runs 24/7: `/health` is off the database.** The gateway's `/health` ran a real `SELECT 1` behind a 10-second TTL cache — exactly `readinessProbe.periodSeconds` — so the cache expired as often as the probe fired and nearly every probe opened a Postgres session. With `minReplicas: 2` that's a database round-trip every few seconds, and any session resets Neon's ~5-minute scale-to-zero timer, so the prod compute never suspended once between 2026-06-21 and 2026-08-01: **373.19 CU-hours / $82.85 billed for a 35 MB database with ~500 lifetime row writes** (0.5 CU held 24/7 = 373 ÷ the 744 hours in July). Confirmed from production logs — 52 `GET /health` hits in 2 minutes on a *single* pod, ~1 ms on cache hits with ~80 ms outliers where the us-east-1 round-trip actually happens. `/health` is now process-level only; the new `/health/deep` keeps the DB check with the TTL raised to 60s. **No manifest or monitor changes needed** — the Kubernetes probes and the UptimeRobot monitors already point at `/health`. Taking the DB call off the probe path also closes an availability hole: a liveness probe that fails on a transient DB blip restarts otherwise-healthy pods, turning a brief database hiccup into a gateway outage. Regression-guarded by a test that patches `SessionLocal` to raise, so `/health` fails loudly if a DB call creeps back. Expected steady state ~$25–30/mo, set by the `*/15` evidence-anchor CronJob's duty cycle rather than continuous uptime. This is **not** a capacity reduction — `autoscaling_limit_max_cu` stays at 8 — so it doesn't conflict with the over-provisioning policy from #340. (#416)
- **`/health/deep` exempted from rate limiting.** The endpoint added in #416 was never added to `_RATE_LIMIT_EXEMPT_PATHS` alongside `/health`, so the database check an operator curls during an incident could come back 429 — exactly when the per-IP limit is most likely to be exhausted, and when you least want the DB check to be the thing that fails. Follow-up to #416.
- **GKE deploys unbroken: `liboqs-python` pin bumped 0.15.0 → 0.16.0.** Version 0.15.0 vanished from PyPI (only 0.16.0 remains), failing every deploy at the Mandate image's `pip install` step — first hit by the #404 deploy, unrelated to that PR's content. - **CPEX OCSF audit plugin v0.0.3: merged #1661 attestation shape, real DSSE signer, `authority_uid`.** `integrations/cpex-ocsf-audit` now emits the attestation carrier as merged into OCSF 1.9 — `attestation_list[]` holding `fingerprint` / `prev_event` / `signatures` objects — retiring the pre-merge draft shape (string `entry_hash` / `prev_entry_hash`, singular `signature`), which no longer exists in the schema. Enum ids verified against ocsf-schema `main` 2026-07-31 (`digital_signature.algorithm_id` 3 = ECDSA, `serialization_id` 5 = DSSE — a different enum than `fingerprint.algorithm_id`, where 3 = SHA-256). New `authority_uid` config names the party the signing credential belongs to and sits inside the hashed bytes, so the claimed authority cannot be swapped post-hoc; signature bytes + JWKS `kid` ride in `unmapped` pending [ocsf-schema#1709](https://github.com/ocsf/ocsf-schema/pull/1709). The verifier rule ships as running code (`sign::signing_input` + `sign::dsse_pae`); 21/21 tests including a full offline-verification round trip; no key material in the repo — demo/test keys are generated at runtime from fixed scalars. Fixed without rewriting a single stored hash (the append-only trigger stays honest): every audit row is now stamped at write time with a **fingerprint of the key that hashed it** (`audit_log.key_fingerprint`, SHA-256[:16], derived metadata — not part of the hashed payload); **regeneration retains the old key** in `organizations.forensic_key_history` instead of discarding it (retired keys are returned to org admins by `GET /orgs/me/forensic-verify-key`, and the regenerate response warns properly); server-side `verify_chain`/`verify_global_chain` pick the right key per row (current → retired → platform) and report intact chains with a `legacy_key_entries` count; exports carry per-event fingerprints plus a report-level `verification_key_fingerprint`; and the CLI (v1.2.0, still stdlib-only) accepts extra epoch keys via repeatable `--key`, reports rows from epochs you don't hold as **"partial key coverage"** (exit 0 — structure fully checked, coverage stated honestly) instead of CHAIN BROKEN, returns **NOT VERIFIED / no key coverage** (exit 1) when the supplied keys cover *nothing* so a typo'd key can't masquerade as a pass, and prints a **KEY MISMATCH** diagnostic when everything fails from entry #1 on a fingerprint-less legacy export. Migration `e2f3a4b5c6d7` (two additive nullable columns) + `scripts/backfill_key_fingerprints.py` stamps legacy rows (metadata-only, dry-run supported). Bundle README documents key epochs. Already-issued bundles verify exactly as before.
- **OCSF export: genesis event no longer emits the literal `GENESIS` sentinel as a fingerprint value.** The chain's first row stores `"GENESIS"` in `prev_hash`/`prev_hash_org`, and the emitter passed it through verbatim — producing a `prev_entry_hash` fingerprint whose `value` isn't a hash (`{"algorithm_id": 99, "algorithm": "HMAC-SHA-256", "value": "GENESIS"}`, seen in the production export at org chain seq 1). `select_chain` now treats the sentinel as a missing predecessor, so the genesis event simply omits `prev_entry_hash` — the same shape as a row with no chain history. Chain *verification* (CLI verifier, `common/audit`, backfill scripts) reads the raw DB columns and still uses the sentinel — unchanged. The reference-bundle validator (`regenerate.py`) keeps accepting the sentinel on seq 1 for backward compatibility with the already-shared bundle revision; the README honest-limitations note gets updated once a post-fix export is regenerated.
- **Case File verifier gives a "wrong file" hint instead of a false tamper alarm.** Dropping an `evidence-anchor/` file (`checkpoints.json` / `inclusion-proofs.json`) or a JWKS file onto the server-side "Verify a Case File" panel used to return "Chain broken / Signature invalid" — reading like tampering rather than the wrong file, a bad moment in a live court/customer demo. The panel now sniffs the JSON client-side *before* uploading (`sniffCaseFile`): a real Case File report is an object carrying the audit `events[]`/`entries[]`; a bare array is `checkpoints.json`, `{proofs}` is `inclusion-proofs.json`, `{keys}` is a JWKS file — wrong files get a friendly message routing the user to the inclusion verifier, and invalid JSON is caught too. Valid reports upload exactly as before. Frontend only. (#357)
- _Forensics:_ the Evidence Anchor checkpoint cron no longer runs `SELECT DISTINCT org_id` over the whole `audit_log` table every tick and then probes every org. It now selects only orgs whose latest `audit_log.id` is ahead of their checkpoint high-water mark — one set-based query that skips idle orgs entirely and reuses the same mark to seed each drain (`after_id`), so the `max(last_audit_id)` lookup never runs separately. Follow-up to the #346 N+1 fix; the remaining P95-latency lever on `/api/internal/evidence-anchor/checkpoint`. The run-summary field `orgs_scanned` is now `orgs_with_backlog`. Internal tooling only — no product impact.
